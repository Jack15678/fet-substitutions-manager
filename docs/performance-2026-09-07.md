# 学校 Linux 服务器性能验证 · 2026-09-07

**主功能补测：**「新增並分析 → 核对 → 确认」的完整接口链结果见 [2026-09-08 主流程报告](performance-main-flow-2026-09-08.md)。下表的“缺席分析接口”只测已有个案重新分析，不是新增按钮的完整耗时。

**已在学校服务器完成优化前后验证；正式服务尚未部署这些改动。** 本报告替代此前的 Windows 本地预验证结论。真实学校数据快照回放中，人工安排接口耗时下降 58.6%，记录页下降 52.6%；1,000 条历史记录的增长场景中，记录页由 47.3 秒降到 0.55 秒。

## 环境与方法

连接依据为 [学校服务器 Runbook](SCHOOL_SERVER_RUNBOOK_ZH_HK.md)，并实际核对了主机环境、运行容器和代码内容：

- 主机：Ubuntu 20.04.6 LTS，Linux 5.15.0-67-generic。
- CPU：Intel Pentium G3240 @ 3.10GHz，2 个逻辑核心；内存约 3.76 GiB。
- 运行时：现有生产 Docker 镜像，Python 3.13.15、SQLAlchemy 2.0.51、SQLite 3.46.1；单 Uvicorn 进程，与正式容器一致，无额外 CPU／内存限制。
- 优化前版本：`06c614227b34121ada68adf64e98f712761bb39f`。确认正在运行的容器中两份业务文件与此检出版本相同。
- 优化后：复用同一个镜像，仅覆盖本次改动的两份业务文件，不更换依赖或运行配置。

使用 SQLite backup API，从只读挂载的学校数据库生成一致快照。两版均在学校主机的隔离容器中串行运行，使用相同快照；模拟学校也使用固定数据。每条路径预热一次、测量 7 次，报告中位数，并保留全部原始样本。cProfile 单独执行，不计入耗时样本。测试不与计时负载并行运行。

HTTP 基准启动实际 FastAPI/Uvicorn 应用，用随机生成的临时账号登录，包含正常的 cookie 鉴权、路由、数据库查询、业务计算、JSON 编码和读取响应体；通过容器回环地址请求。**这些数字不包含 Nginx、校内网络及浏览器渲染，也不是并发压力测试。** 正式站点和教师账号未用于压测。业务调用基准另外记录 SQL 次数。

## 真实学校数据快照回放

数据规模：63 位教师、3 个课表版本、2,725 堂课、3,212 个教师时段、11 条缺席、33 个调动、58 条调动明细。选择有效或已解决缺席最多的日期 2026-06-10（2 个个案），排除已取消个案。为重复回放历史业务，路由时钟固定为该日 00:00；这不是宣称现在正式站点的实时延迟。

| 接口 | 优化前中位数 | 优化后中位数 | 耗时下降 |
|---|---:|---:|---:|
| 有效课表接口 | 130.401 ms | 75.643 ms | 42.0% |
| 缺席分析接口 | 161.464 ms | 150.566 ms | 6.7% |
| 人工安排接口 | 640.333 ms | 264.965 ms | 58.6% |
| 记录页接口 | 144.709 ms | 68.633 ms | 52.6% |

人工安排的业务查询从 **97 次降为 42 次**。单日有效课表业务耗时从 40.963 ms 降到 16.876 ms；因真实数据包含来自其他星期的调入课，查询为 5 → 6，新增的 1 次查询批量读取所有缺失原课，避免逐条补查。分析窗口课表为 82.194 → 69.071 ms。

缺席分析接口的改善较小，前后样本范围有重叠；不把 6.7% 当作稳定承诺。人工安排和记录页改善幅度明显，全部样本见原始 JSON。

## 历史数据增长场景

固定模拟学校：60 位教师、30 个班、每周 1,350 堂课、1,350 个教师时段、4 位同日缺席教师、17 堂待安排课程、1,000 条历史代课记录。日期为 2026-09-07，时钟固定在当天 00:00，历史记录均在此前。

| 接口 | 优化前中位数 | 优化后中位数 | 耗时下降 |
|---|---:|---:|---:|
| 有效课表接口 | 191.244 ms | 42.179 ms | 77.9% |
| 缺席分析接口 | 1,263.229 ms | 620.184 ms | 50.9% |
| 人工安排接口 | 2,939.661 ms | 814.995 ms | 72.3% |
| 记录页接口 | 47,305.437 ms | 551.334 ms | 98.8% |

人工安排业务查询从 **218 次降为 42 次**。记录页 47 秒的瓶颈是在学校服务器 HTTP 基准中实际发现的，未用 Windows 数据替代。此场景用于说明数据增长后的表现，不冒充学校当前已有 1,000 条记录。

## 瓶颈与改动

1. **有效课表读取过量。** `effective_occurrences` 原来读取完整周课表和所有已确认历史调动，并逐条扫描本次课表。现在按请求星期和调动来源／目的日期筛选；跨日期调入的原课统一补读一次，保留原有处理顺序和完整调动链。
2. **人工安排重复读取同一天的数据。** `_manual_cover_context` 在同一次请求内共享教师、任教学科、缺席、累计代课数和节次信息；相邻授课数复用已有占用索引。新请求和确认操作仍读取最新状态。
3. **记录页反复扫描后续调动。** `_has_confirmed_downstream_adjustment` 原来为每个调动加载全部后续调动，造成随历史增长的二次方工作量。现在用数据库条件直接查找课堂／日期／节次匹配的后续记录，找到一条即停止。已完成的记录无需做撤销依赖检查；历史／未来日期无需读取当天节次配置；批量详情共用已读取的教师姓名。

改动落在共享函数，覆盖记录页、有效课表详情、调动列表及撤销校验的相关调用。权限、推荐规则、搜索上限、过滤／分页结果和撤销约束保持不变。没有跨请求业务缓存、新依赖或数据库迁移。记录页仍按现有规则在内存筛选和分页；本次消除的是已测得的重复读取和后续记录扫描。
