# 需求與決策日誌

本文件按討論日期記錄需求、出現原因、目的、已作決策及仍待處理事項。內容重點是保存決策脈絡，不代替簡潔的開發進度表。

## 2026-08-10

### 1. 產品定位

需求最初源於學校需要處理教師臨時不能上課的情況。系統不是讓全體老師自行使用，也不是自動發布代課，而是供校長、副校長和指定排課老師使用的決策工具。

目標流程確定為：

1. 獲授權使用者輸入缺席老師、日期及節次；
2. 系統從正式課表找出受影響課堂；
3. 系統計算可行調課／代課候選；
4. 顯示候選方案及原因；
5. 管理人員人工確認；
6. 保存調整後的有效課表及歷史。

這個定位的原因是學校排代課存在臨時情況和行政判斷，系統應協助決策而不是取代負責人。

### 2. 開源項目選擇及使用方式

研究後選擇以 `fet-substitutions-manager` 為基礎，因為它已有 FastAPI、Vue、登入、權限、資料庫、Docker 和基本代課業務骨架。其原有前端和代課規則不符合學校需求，因此只把它視為 Web 應用底座。

項目採用 AGPL-3.0-or-later。修改後透過網絡提供服務時，需向實際使用者提供對應源碼；教師資料、課表、資料庫、密碼和伺服器設定不屬於需要公開的源碼。

部署形式確定為私有雲端 Web App，只有少量管理人員帳號。學校官網和代課系統分離，建議使用獨立子域名。第一版不建立全校老師帳號，也暫不開發即時通知 App。

### 3. 真實課表來源

學校提供三份課表：

- `25-26班別時間表(全日制).xls`
- `25-26教師時間表(全日制).xlsx`
- `25-26教師時間表(全日制)_值日.xlsx`

班別表用作課堂主來源，教師表用作教師時段及交叉核對。值日版主要增加值日、小息等安排；經確認，這些不等同正式授課，不應直接把老師判定為不能調課，因此目前不匯入值日版。

系統只把九個正式教學節次視為教師忙碌。班別表和教師表不一致時不猜測，受影響課堂鎖定為不可自動調動。

首次匯入結果為：25 個班、55 位教師、1,050 堂班別課、1,299 個教師時段；發現的精確不一致課堂保留並鎖定，避免系統錯誤判斷老師空閒。

### 4. 核心調課優先次序

學校實際規則不是優先找同科老師代課，而是優先維持同一班原有老師和教學進度：

1. 若 A 老師上午缺席、下午可以上課，而 B 老師下午教該班且上午有空，優先把兩堂課同日互調；
2. 若 A 老師全日缺席，優先和下一個上課日該班的課互調；
3. 下一個上課日無解，再搜尋之後的上課日；
4. 越早結束整個缺席需求越好；
5. 直接互調無解時可考慮同班三堂循環；
6. 同科但平時不教該班的老師，因進度和學生熟悉程度不同，只能作迫不得已的最後選項。

所有已確認調課必須覆蓋到「有效課表」。新需求只能以有效課表計算，不能繼續把原 Excel 中已被占用的時段視為空閒。

### 5. 候選搜尋及整體選擇

候選產生採用確定規則，不使用隨機和 LLM：同日直接互調、同班三堂循環、逐個未來上課日搜尋，最後才是同科緊急代課。

每個方案須通過硬限制：教師和班別不能重複、缺席教師不能被移到缺席時段、停課日不可排課、已確認和資料不一致課堂不可再移動。

若同一缺席包含多堂課，系統要整體選擇互不衝突的方案，排序目標為：解決最多課堂、最早完成、移動最少課堂。管理人員逐項確認後，系統重新分析剩餘課堂。

### 6. 第一版功能及介面

新工作台已包含：Excel 匯入預覽、輸入缺席、候選方案、人工確認、有效課表、人工 2／3 堂互調、歷史撤銷和停課日。

介面目標是讓管理人員看到「為甚麼推薦」及每個方案實際移動哪些課堂，不使用只有老師姓名的下拉框或黑箱分數。

### 7. 原項目功能取捨

確認大概率或肯定不需要：

- 原有 FET XML 流程；
- 原有按值班／空堂分類並隨機選人的傳統代課；
- 舊代課優先級；
- 考試排程；
- 考試監考／值班分配；
- 多學校操作介面。

舊 PDF、統計和報告暫時保留程式碼但隱藏入口，等待新調課資料的替代報表完成後再決定是否刪除。舊功能不應繼續掛載後端路由，避免新舊資料並行寫入。

仍需要或要以新模型重做：

- 年級活動、某班停課及因此釋放老師；
- 長期病假／產假，使用開始日期、結束日期及全日／指定節次；
- 學年／課程年度；
- 用戶和個人密碼；
- 個人資料清理、匿名化和審計；
- 繁體中文（香港）及英文。

### 8. Excel 匯入可靠性

現有解析器是在閱讀真實課表後寫成的確定程式，伺服器運行時不依賴 LLM。不過目前仍依賴兩份工作簿的固定行列結構。

長期方案確定為：保留已知課表格式的解析器，改用標題和結構特徵辨識；結構不明時停止匯入，不猜測；另外提供一份標準表格範本作保底。完全通用地猜測任意 Excel 被認為風險太高。

匯入畫面應獨立，並逐堂列出兩表差異。第一版要求管理員修正原 Excel 後重新上傳，不在網頁內另建第三套課表資料。

### 9. 日期、歷史和部署要求

未來缺席及確認調課必須保存到資料庫，伺服器重啟或日期經過後仍然存在。過往調課不可直接刪除，撤銷應保留原紀錄、撤銷者和時間。

課表版本必須按查詢日期選擇，否則提前匯入新學年課表會破壞舊日期的歷史。伺服器時間應以 UTC 保存、以香港時區顯示；若要判斷當日已過節次，還需另行設定每節開始和結束時間。

部署採用 Docker Compose、Caddy HTTPS 和持久化 `data/` 目錄。少量管理人員使用時 SQLite 足夠，重點是每日備份、保護 `.env`、限制帳號和保留審計。

## 2026-08-11

### 1. 舊功能正式退場方式

決定先隱藏並停止掛載舊功能，而不是立即刪除檔案。原因是新系統尚在試點，舊程式仍可能為 PDF、統計或資料處理提供參考；停用路由已能消除誤操作和主要攻擊面。

已從主要介面移除舊代課、班別釋放、監考、考試、舊 PDF、舊統計和舊說明入口。後端只掛載登入、必要設定、用戶、學年、資料治理和新調課路由。機構管理頁和個人機構切換亦已隱藏，但資料目錄仍保留固定機構鍵，避免無收益的大規模資料庫重構。

### 2. 下一階段優先次序

開發次序確定為：

1. 修正課表版本按日期生效及香港時區；
2. 拆出課表匯入中心；
3. 顯示逐堂不一致資料；
4. 改良 Excel 結構辨識並提供標準範本；
5. 建立未來／今日／過往記錄；
6. 加入長期病假／產假；
7. 加入年級活動、班別停課及釋放老師；
8. 新 PDF、Excel 匯出及統計。

### 3. 文件維護要求

從本日起維護兩份文件：

- `DEVELOPMENT_PROGRESS.md`：簡潔記錄已完成、進行中、未完成及停用範圍；
- `REQUIREMENTS_LOG.md`：按日期詳細保存需求出現的背景、目的、決策和變更原因。

每完成一項功能或作出範圍決策，兩份文件需在同一批改動中同步更新，避免程式實況和需求記錄分離。

### 4. 按日期選擇課表版本

已將「單一目前版本」改為每個查詢日期選擇生效日期不晚於該日的最新版本。同一次搜尋若跨過新學年生效日，每天亦會各自使用正確版本。

這項修正的目的是讓學校可以提前匯入新學年課表，不會破壞過去日期的有效課表和調課歷史。教師下拉名單也改為根據缺席日期所屬課表版本產生。

### 5. 時區規則

新調課、撤銷和審計時間明確以 UTC 寫入現有 SQLite `DateTime` 欄位；API 傳回帶 `Z` 的 UTC 時間，前端以 `Asia/Hong_Kong` 顯示。介面預設「今日」和後端默認查詢日亦改用香港日期。

這一階段不處理「當日已過節次」，因為學校尚未提供每節正式開始和結束時間設定。

### 6. 獨立課表匯入中心

匯入功能已從調課工作台移至獨立管理畫面。管理員上傳兩份課表後，畫面顯示班別、教師、課堂和鎖定數量，再逐堂列出不一致資料。

每項差異包含星期、節次、班別、科目、教師、班別表內容及教師表內容。無法辨識教師的資料會阻止啟用；兩表不一致但仍可讀取的課堂可由管理員知情啟用，但系統會鎖定它們。

實際三份學校課表再次核對後，仍得到 25 班、55 位教師、1,050 堂課和原本 5 項不一致，確認新顯示並沒有改變匯入結果。

### 7. Excel 結構辨識改良

解析器不再以第 5、7、9 行等固定行號取課。現在會：

1. 搜尋星期一至五標題來定位欄位；
2. 讀取上課時間範圍；
3. 以下一行能否辨識真實教師來區分授課、早會、小息和午膳；
4. 要求每班正確辨識九個正式教學節次；
5. 教師表必須找到和班別表一致的九個上課時間。

因此學校插入標題行、改變行號或移動星期欄時，解析器仍可運作。若結構不能可靠地辨識九節課，匯入會明確停止，不會猜測。標準匯入範本其後改由學校人力設計，詳見下一項決定。

### 8. 標準範本改由人力設計

使用者決定標準課表範本可以由學校人力設計，本階段先不由系統產生範本。程式仍維持現有原則：辨識已知結構；無法可靠判斷時停止匯入並通知管理員，不以猜測方式建立課表。

此決定讓開發先集中在每天真正使用的記錄、長期缺席及介面語言，不代表日後不能再加入標準範本下載。

### 9. 未來、今日及過往記錄

新增獨立「記錄」畫面，以香港時區的當日日期把資料分成未來、今日及過往三個分頁。未來記錄按日期由近至遠排列，過往記錄按日期由新至舊排列；每頁 20 項，API 支援 5 至 50 項的分頁大小。

每項記錄以缺席個案為主，顯示教師、節次、處理狀態、建立者及其下已確認或已撤銷的調課。沒有缺席個案的人工互調亦會獨立出現在記錄中。日期經過、伺服器重啟或使用者翻頁都不會刪除資料，紀錄繼續保存在 SQLite；只有具權限的撤銷操作會改變狀態，原調課內容仍保留。

### 10. 長期病假及產假日期範圍

管理員可以新增、編輯及刪除長期病假、產假或其他長期缺席，設定教師、開始日期及結束日期。現階段按全日缺席處理：範圍內第 1 至第 9 節都視為不可用，候選搜尋、人工互調及連鎖調課都不能把該教師排入目的時段。

沿用原項目的 `professors_baixa` 資料表，避免建立重複模型；新 API 以教師 ID 驗證，保存時仍以唯一教師名稱對應。為減少敏感個人資料，只保存「長期病假／產假／其他」分類，不提供診斷或醫療詳情欄位。長期缺席清單及修改入口只向管理員顯示。

### 11. 繁體中文（香港）及英文介面

主介面、登入頁、調課工作台、課表匯入、記錄、長期缺席、個人密碼、學年、用戶和資料治理頁面均接入繁體中文（香港）及英文。首次使用和舊有西班牙語／加泰羅尼亞語設定都會安全回落至繁體中文；登入頁及登入後導覽列可以切換語言，選擇保存在瀏覽器。

前端不再載入西班牙語或加泰羅尼亞語語言包，因此它們不會出現在語言選單或登入畫面。舊翻譯檔暫時留在倉庫供原頁面參考，但已不屬於可運行介面。

其後發現瀏覽器分頁仍使用舊加泰羅尼亞語 HTML 標題。已把預設分頁標題及 HTML 語言標記改為繁體中文，並在切換介面語言時同步更新分頁標題。

### 12. 缺席教師名單按日期同步

使用者發現「缺席教師」有時無法選擇。資料庫及 API 核對後確認生效課表和 55 位教師均存在；問題是工作台只在初次載入時以伺服器今日判斷課表是否生效，之後更改缺席日期只更新教師清單，沒有同步更新該日期所屬的課表版本，因而可能沿用錯誤的停用狀態。

工作台現改為以缺席日期同時查詢生效課表及教師名單。切換頂部日期或表單日期後，兩者會一併重載；該日期有生效課表時可選教師，沒有生效課表時才停用教師選擇。日期欄本身會保持可編輯，避免使用者選到尚未有課表的日期後無法返回，亦避免未來或過往日期被當成今日處理。

### 13. 課表適用日期及校曆來源

學校提供的班別表和教師表只描述星期與節次，沒有學期開始日期，因此系統不能可靠地從 Excel 推算課表何時生效。現有版本的 2026-08-10 是啟用匯入時輸入的日期，不是解析器判斷所得。

匯入中心原本已有生效日期欄，但預填香港當日容易令人誤以為系統自行決定。現改為開始及結束適用日期均空白必填，管理員明確指定完整日期範圍後才可檢查及啟用。

使用者提出上傳校曆以自動判斷假期。方向確定為「上傳校曆、解析停課日期、預覽、管理員確認」，確認後才寫入現有停課日資料；不能只套用公眾假期，因為學校另有教師發展日、校內活動及補課日。校曆格式未定，需取得實際檔案後才實作解析，避免對合併儲存格、顏色或自由文字作不可靠猜測；現有手動日期清單保留作修正及後備。

### 14. 已上傳課表版本管理

使用者要求已上傳課表支援增、刪、查、改，並正確處理牽涉的記錄。匯入中心現列出每個版本的適用日期範圍、來源檔案、課堂及教師數量、相關缺席及調課記錄數，並標示目前使用版本。

新增版本繼續使用兩份 Excel 的預覽及啟用流程，並必須指定開始及結束日期。版本日期範圍不可互相重疊；課堂內容不提供逐格修改，需重新匯入新版本，讓原始 Excel 保持唯一資料來源。

只要版本適用範圍內有缺席個案，或調課明細的日期／原課堂引用該版本，即使調課已撤銷，版本仍不可刪除。日期範圍可以延長或調整，但新範圍必須繼續包含所有相關記錄，否則拒絕儲存。刪除未使用版本時才會一併刪除該版本的課堂及教師時段；操作均提升課表修訂號並寫入審計記錄。

舊資料庫會自動加入可空白的結束日期欄，避免升級時猜測學年結束日。既有版本在管理員補填前沿用開放式結束日；所有新匯入版本則必須有明確結束日期。

### 15. 測試階段缺席及調課記錄管理

使用者要求測試期間能對缺席及調課記錄增、刪、查、改。新增及查詢沿用工作台和記錄頁；管理員現可在記錄頁修改缺席教師、日期和節次，或完整刪除缺席。由於已產生的調課方案是按原缺席條件計算，修改缺席時會在同一個資料庫交易內刪除其全部調課明細並把個案重設為待處理；完整刪除缺席亦會連帶刪除其調課，避免有效課表留下殘餘變動。

調課記錄可修改原因、撤銷或完整刪除。完整刪除會移除所有調課步驟、即時回復基礎有效課表，並把相關缺席重新標示為待處理。系統不提供逐格修改已確認的互調步驟；如方案本身錯誤，刪除後重新分析或確認，避免只改其中一段而形成不完整互調。完整刪除仍寫入審計記錄，方便確認測試資料由誰清理。

### 16. 班別表與教師表差異由管理員裁決

使用者指出匯入預覽雖列出「需核對」項目，卻沒有讓管理員決定哪份資料真實。每項可處理差異現提供「採用班別表」及「採用教師表」兩個選擇，所有項目完成裁決後才可啟用課表；姓名無法辨識或班別課堂沒有教師等結構錯誤仍須回到原 Excel 修正，不能以按鈕繞過。

採用班別表時，系統保留班別課堂的班別、科目及教師，並把該教師同星期、同節次的教師表時段改成這項安排。採用教師表時，系統保留教師自己的時段，從有爭議的班別課堂移除該教師；若班別因此沒有已知教師，課堂仍保留但鎖定，不會猜測另一位教師。系統亦拒絕同一教師同一節同時採用兩個班別表安排。

每項選擇會保存到課表版本的 `resolutions_json` 及啟用審計記錄。舊資料庫自動新增該欄位；實際課表重新預覽後正確列出 5 項帶唯一裁決編號的差異。原本顯示「2 個教師／節次」但表格有 5 行的統計方式亦已修正，警告數量改為直接使用實際待核對項目數。

### 17. 工作臺互動、狀態保存及字體調整

使用者在 2026-08-12 提出以下介面及流程問題：長時間分析時按鈕只有載入圖示，無法感知處理仍在進行；選到沒有適用課表的日期時，教師選單雖不可用但原因不清楚；工作臺同時顯示調課歷史和停課日期輸入，與每日安排工作的職責混在一起；分析後切換頁面會令未確認進度消失，而記錄頁的待處理缺席亦沒有返回工作臺續辦的入口。

本階段決定把「檢查課表」改名為「對比時間表差異」，並與「分析全部課堂」共用由左至右的半透明估算進度動畫。現有 API 是單次同步請求，沒有可供前端顯示的真實百分比；因此不新增背景任務或串流介面，動畫只表示系統仍在處理，不顯示數字百分比，完成或失敗後恢復原按鈕。

工作臺只在切換主頁籤時隱藏而不銷毀，保留已選教師、日期、節次、分析結果及候選方案。瀏覽器重新整理後不保存精確候選選擇，但缺席個案仍已存入 SQLite；記錄頁會為待處理個案提供「繼續處理」，重新載入該個案並按最新有效課表分析。日期變更期間立即清空舊教師名單；若日期不屬於任何課表版本，教師選單停用並顯示「所選日期未有課表資料」，不再額外顯示重複的頁面提示欄。

「已確認／已撤銷調課」只在記錄頁管理，工作臺入口移除。「停課／假期日期」自由文字輸入亦從工作臺移除，既有停課資料表、驗證規則及 API 繼續保留。後續需求確定為由管理員上傳實際校曆，系統辨識候選假期及停課日、顯示預覽，再由管理員確認寫入；取得實際校曆格式前不猜測其版面，也不在本階段實作解析。

繁體中文介面改用裝置已有楷體字棧，涵蓋頁面、表格、表單及按鈕；英文介面保留現有系統黑體。為避免增加首次下載量及字體授權維護，本階段不把第三方中文字體放入倉庫，不保證 Windows、macOS 及手機顯示完全相同。

教師表的「共同備課」位於正式教學節次科目列，現有解析會建立不可移動的教師忙碌時段；有效課表衝突驗證亦會拒絕把其他課堂移入該時段。本階段不改演算法，只新增回歸測試，避免日後解析器調整後把共同備課誤當空堂。

### 18. 教師表額外授課及共同教師核對

使用者發現關錦珊在教師表的星期四第 2、3 節列有 3C 中文，但班別表相同課堂只列韓詠炘。原核對只由班別表反查其教師是否出現在教師表，沒有由教師表反查額外教師，因此關錦珊只被保存為忙碌，沒有加入 3C 課堂；登記她缺席時亦找不到需要處理的課堂。

匯入核對改為雙向：既保留原有「班別表教師在教師表不吻合」，亦逐項列出「教師表同班同節多出教師」。後者由管理員選擇採用教師表時，把該教師加入班別課堂的共同教師名單；選擇採用班別表時，忽略該教師表授課格。所有額外教師都必須逐項裁決後才可啟用，決定繼續保存於課表版本及審計記錄。

以學校現有兩份課表全量核對，共列出原有 5 項班別表教師不吻合，以及 179 個教師表額外授課格；184 項均有唯一裁決編號。關錦珊星期四第 2、3 節的兩項在採用教師表後，會與韓詠炘共同保存為 3C 中文的課堂教師。

教師表中的共同備課、康樂活動等不是正式班別代碼的活動繼續只作忙碌時段，不列為共同教師差異。兩表同班同節的科目文字亦不在本次擴大裁決，因導修／輔導及分組教學常有合理的科目名稱差異；本次只修正能明確、安全裁決的額外教師關係。

### 19. 開發服務重新載入及宋體介面

使用者重新對比課表時仍只看到原有 5 項差異。檢查後確認正在監聽 8000 埠的 Uvicorn 以不帶自動重載的舊進程運行，因此它未載入已完成的雙向核對程式；資料和新規則本身沒有失效。開發伺服器改以自動重載模式啟動，讓後續修改後不再沿用舊 Python 進程，正式雲端部署則仍應在發布時明確重啟服務。

使用者其後決定不再使用楷體，繁體中文介面全域字體改為裝置已有的宋體／明體字棧，涵蓋登入頁、導覽、表格、表單及按鈕；不下載或加入新的字體檔。英文介面仍沿用系統黑體。

使用者觀察課表對比通常需較長時間，原 8 秒估算動畫前進過快；經試用後最終把共用進度動畫調整為 20 秒到達約 90%。實際請求成功或失敗時仍立即復原，不等待動畫結束，也不顯示虛假百分比。

### 20. 多名教師缺席、全天缺席及批量核對

使用者提出同一日可能有多名教師同時缺席，逐名登記和分析會重複操作，亦可能令分開計算的方案互相佔用同一教師或課堂。因此工作臺的缺席教師改為可多選，所選教師使用相同日期及缺席節次；「全天缺席」會一次選取第 1 至第 9 節，仍可取消個別節次改回部分缺席。

資料庫繼續以「每名教師一個缺席個案」保存，不把多名教師合併為不可獨立管理的單一記錄。前端一次批量建立或沿用這些個案，後端則把同批個案放入同一次全局候選選擇，避免向不同缺席課堂推薦互相衝突的安排。確認後，各教師的缺席及調課仍可在記錄頁獨立編輯、撤銷及審計。

課表匯入現有 184 項差異若逐項點選效率太低，因此核對表加入逐列勾選、全選及批量採用班別表／教師表。批量操作只填入所選項目的裁決，管理員仍可逐項覆寫；結構錯誤等不可裁決項目不提供勾選，所有可處理差異完成決定前仍不可啟用課表。此功能只重用現有裁決資料格式，不新增資料表或依賴。

### 21. 課表差異逐項確認及現行介面語言清理

使用者指出批量選擇雖可加快填入決定，但系統仍要求一次完成全部項目才可確認，容易令已核對的工作在切頁後失去進度。因此每項差異加入獨立「確認此項」，勾選多項後亦可按「確認所選決定」批量保存；已保存的決定保留在匯入預覽資料中，尚未保存或其後改動的項目則繼續標示為未確認。

部分確認只代表核對進度，不會建立或啟用課表版本。畫面持續顯示已確認、總數及餘下項目，並明確說明課表尚未生效；只有全部可處理差異已保存，且沒有必須修正原 Excel 的錯誤時，管理員才能按「確認啟用」。這樣可以中途保存工作，同時避免半套裁決流入有效課表。

批量操作文字會跟隨所選差異類型。一般兩表不一致顯示「採用班別表／採用教師表」；教師表額外授課格則顯示「忽略額外教師／加入為共同教師」；混合選取時使用中性的「左側決定／右側決定」，避免把共同教師操作誤寫成採用整份教師表。

使用者亦要求清除其他西班牙語內容。現行繁體中文／英文頁面、登入、個人資料、學年、用戶及資料管理 API 會直接顯示的舊西班牙語／加泰羅尼亞語錯誤訊息已改為繁體中文，HTML 搜尋引擎描述及 API 名稱亦同步更新。未載入的 `ca.json`／`es.json`、舊頁面原始碼、註解及內部欄位名稱繼續保留，因它們不會出現在目前介面，亦有助日後追蹤上游程式。

### 22. 缺席重新分析、受影響課表及特殊課程優先級

使用者要求工作臺文案更貼近日常操作：「輸入缺席」改為「缺席老師」，日期欄標示為「缺席日期」，第二步改為「查看並人工確認建議」，「候選方案」改為「可選方案」。缺席老師欄繼續支援多選，並修正下拉選單的標籤結構及日期變更事件，確保可正常開啟和選擇。

原流程在同一老師及日期已有缺席個案時會直接沿用第一次保存的節次。因此使用者誤選一個沒有課堂的節次、分析後再改選其他節次，後端仍按舊節次計算，畫面看似沒有反應，必須先取消缺席。批次分析入口現會以畫面提交的最新節次更新既有個案後再分析；若該個案已有已確認調課，才拒絕直接修改並要求先撤銷，避免破壞已鎖定安排。

「有效課表」改名為「今天受影響的課表」，預設只列出當天已有確認調動的老師／班級，不再把整日課表逐行展開。卡片模式按班級及調課組合顯示「原本第幾節 → 現在第幾節」；小型班級課表模式只列受影響班級，紅格以「調整」列出原科目及老師，綠格以「改為」列出調整後科目及老師，代課則保留獨立標示。完整課表仍可由管理員切換查看及進行人工互調。取消缺席及撤銷調課不再出現在一般記錄清單，但資料仍保留於資料庫及審計紀錄。

部分課程跨日調動可能要求學生提前準備，例如體育、視藝、美術及中英文默書。課表匯入核對結果新增「特殊課程標註」：系統按科目名稱預選常見項目，管理員可在啟用前增減。標記保存到每堂基礎課；候選只要把特殊課程移到其他日期，就排在不涉及特殊課程跨日移動的可行方案之後，同日互調不受影響。全局方案選擇亦把特殊課程跨日移動數放在完成日期及移動堂數之前比較，但教師、班別、缺席及停課日等硬限制保持不變。

特殊課程設定以課表版本為單位。已上傳的舊版本會列出該版本實際科目，管理員可展開勾選並沿用原「儲存」操作更新；即使版本因有相關記錄而不可刪除，仍可調整此優先級標記。更新只影響之後重新分析產生的候選排序，不改寫已確認或歷史調課。

若管理員上傳檔案並完成分析後發現選錯，核對結果提供「取消這次上傳」。此操作只刪除尚未啟用的 `timetable_import_previews` 預覽、已保存的核對進度及前端檔案選擇，不刪除任何已生效課表版本。課表啟用、取消預覽和修改舊版本特殊課程均寫入審計紀錄；本輪調課測試增至 19 項，前端正式建置通過。

### 23. 管理員統計、空堂代課、環形調課及每日匯出

使用者在 2026-08-18 確認左側導覽新增只向管理員顯示的「數據統計」頁。頁面按已設定的學年選擇資料範圍，以教師為列、月份為欄顯示每月次數及學年合計。其後在 2026-08-23 明確統計口徑：只計由缺席個案產生、已確認且未撤銷的安排；缺席老師本人不計，二堂或三堂互調中的每名受影響老師各計一次，同一安排內同一老師最多一次；緊急代課只計實際代課老師。沒有連結缺席個案的人工互調不計。月份按受影響老師調整後實際上課日期計算。

找不到有效的二堂或三堂互調時，預設後備方案改為在目標節次沒有課、沒有其他不可移動工作、亦沒有缺席或長期休假的老師中安排代課，不再以同科作硬限制。候選先按相鄰課節的空閒程度排序：前後課節均沒有課、只有一邊沒有課、其餘目標節次空堂；第 1、9 節只檢查實際存在的相鄰課節。同級候選再以同科老師及本學年累計參與次數較少者優先。連空堂老師也找不到時，缺席才保留為待人工處理。

「今天受影響的課表」不再以一般卡片逐行列出調課，而以受影響課堂的有向連結顯示。每個 node 代表一堂具日期及節次的課，箭頭代表課堂移往下一個 node 原有的時段；所有「調課」記錄必須是最少兩個 node 的完整閉環，例如 `A → B → A` 或 `A → B → C → A`，跨日調課亦顯示完整閉環。緊急代課是原節次更換教師，不屬於調課環，繼續以獨立的單堂「代課」記錄顯示。現有調課步驟已能表達 node 與連結，實作時不另建圖資料模型。

管理員可按選定日期輸出學校提供的「調課／代課表」版式。表頭包括學年度、代課日期、星期及請假教師；原因保留空白。表格包括班主任課、第 1 至第 9 節、一息、午膳及二息，以及節次時間、班別、科目、代課教員、簽署和附註；簽署留空供列印後填寫。班別及科目按缺席老師的原課表帶入，代課教員則按已確認安排帶入該節實際上課老師。互調課的附註自動寫明「與 YYYY-MM-DD 第 N 節（老師）對調」；三堂閉環標示為「連鎖互調」，讓對應老師知道需要簽名。緊急代課不屬於互調，附註保留空白。

同一份資料提供兩種匯出格式：Excel 匯出為一個 `.xlsx` 活頁簿，每名缺席老師一個工作表；PDF 匯出則每名缺席老師一個獨立 PDF，只有一人時直接下載該 PDF，多人時以一個 ZIP 包含全部 PDF。第 1 至第 9 節的開始及結束時間由管理員設定，首次使用可採用參考表的時間作預設；Excel 和 PDF 共用同一份節次設定及資料整理結果，避免兩套格式出現內容差異。

本輪已於 2026-08-19 完成管理員統計、兩種每日匯出、節次時間設定，以及最少兩個 node 的完整調課閉環顯示。上述「找不到互調方案時改用任何合資格空堂老師」仍留待下一輪實作；目前後備方案仍沿用同科老師限制。

使用者在 2026-08-20 要求管理員確認候選方案前可以核對涉及老師的課表。每個候選方案的「確認這個安排」旁提供核對入口，暫時直接由系統現行有效課表及所選候選步驟重建確認後課表；按涉及老師及相關日期顯示第 1 至第 9 節，只保留沒有改變的課及方案產生的新安排，新安排統一標示為「調整」，不使用「移入／移出」字眼。完整閉環不在核對對話框重複顯示，繼續只在「今天受影響的課表」展示。

### 24. 配置頁、長期缺席位置及學年空白狀態

使用者在 2026-08-23 要求把「節次時間」由數據統計頁拆出，放到可繼續承載其他設定的獨立「配置」頁；每日表區標題改為「導出每日調課／代課表」；長期缺席管理則由記錄頁移至調課工作臺。長期缺席仍沿用原有管理員權限、日期範圍驗證、重疊檢查、課表版本更新及審計記錄，不另建第二套資料流程。

其後確認數據統計的學年下拉空白並非欄位名稱不一致：現有機構資料庫有已生效課表版本，但 `cursos` 表沒有任何學年定義。學年名稱及開始日期不能只憑課表檔名或生效日期可靠推斷，因此系統不自動寫入猜測資料。配置頁改為直接重用現有學年管理功能；統計頁在沒有學年時顯示明確說明和「前往配置學年」入口，並暫停統計及每日導出，避免產生缺少學年度表頭的文件。新增學年後重新進入統計頁即可按該學年載入月份及教師合計。

### 25. 學年明確結束日期及假期雙模式配置

使用者在 2026-08-23 指出學年之間可能有暑假空檔，不能以後一學年的開始日期前一日自動推算上一學年的結束日期。因此新增及修改學年都必須明確填寫開始與結束日期；日期範圍可以不連續，但不可互相重疊。既有結束日期空白的舊資料仍可讀取，管理員必須在配置頁補齊後才可建立會與它重疊的新學年。統計、每日匯出及假期日曆均使用這個明確範圍。

配置頁新增「假期設定」，沿用既有 `school_closures` 停課日資料及調課引擎的跳過規則，不建立第二套假期模型。管理員先選擇學年，再以兩種方式編輯同一份假期清單：輸入一個或多個嚴格 `YYYY/MM/DD` 日期，或在該學年開始至結束日期的全年月曆上直接點選／取消。輸入日期必須屬於所選學年；儲存時只替換該學年的假期，其他學年資料保持不變，重複日期會自動合併。

這項需求取代第 13、17 節原先尚未落實的任意校曆檔案上傳方案。現階段不猜測 Excel、PDF、合併儲存格或顏色所代表的假期；若日後取得固定校曆檔案格式，可再加入專用解析及預覽流程，而不改動現有假期資料與排課規則。

### 26. 配置頁 404 及錯誤提示呈現

使用者在 2026-08-23 發現配置頁顯示 `Not Found`。後端訪問日誌確認是 `GET /api/rescheduling/config` 回傳 404；學年、假期及節次時間 API 均正常。源碼已包含這個調課配置路由，但目前運行中的開發後端沒有完成熱重載，因此不是配置資料遺失。待重啟後端載入新路由即可清除；重啟後現有登入工作階段可能需要重新登入。

現行全域 Axios 錯誤統一用右上角 PrimeVue `Toast` 顯示，短暫、距離操作位置遠，較難發現。可選的現有元件／模式如下：

1. PrimeVue `Message`：在頁面或設定區塊內持續顯示載入、儲存或伺服器錯誤，可附「重試」，適合一般 API 失敗；
2. 欄位錯誤狀態：輸入框套用 `p-invalid`，下方保留錯誤文字，適合日期、格式及必填驗證；
3. PrimeVue `Dialog`：以模態方式顯示必須處理後才能繼續的阻斷錯誤，不用於一般失敗；
4. 全頁錯誤狀態：首次載入整頁失敗時，以 `Message`、說明及重試按鈕取代空白內容；
5. PrimeVue `Toast`：保留給成功、背景完成及不阻斷操作的短訊息。

建議採用分層組合，而不是以另一個單一元件取代全部 Toast：欄位問題就地顯示，區塊／頁面 API 失敗用持續 `Message`，不可繼續的錯誤才用 `Dialog`，成功及次要通知才用 `Toast`。現有 PrimeVue 已包含所需元件，不增加新依賴；通知中心、錯誤抽屜及完整 Snackbar 系統暫不加入，除非日後需要保存大量跨頁通知。
